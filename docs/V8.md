# v8: what it is, and the evidence behind it

## Where the ladder is

This account's ladder record, harvested from Kaggle's episode API on 2026-09-23
(1,336 episodes across all submissions):

| Version | Games | W | T | L | Win share of decided games |
| --- | --- | --- | --- | --- | --- |
| v3 | 170 | 104 | 0 | 66 | 61% |
| v4 | 187 | 97 | 0 | 89 | 52% |
| v5 | 220 | 115 | 0 | 105 | 52% |
| v6 | 403 | 171 | 0 | 232 | 42% |
| v7 | 300 | 150 | 39 | 111 | 57% |

Two facts decide the approach:

1. **The field is a monoculture.** v7 is a byte-for-byte copy of a public notebook,
   and 39 of its 300 games ended in exact ties, because the opponent ran the same
   code and played the same moves. Most of the field is "route-replay" agents: a
   precomputed 719-turn action tape per town-shop layout, plus reactive layers.
   Production is close to identical across them. **Games are won in the market**,
   usually by 0.1-3% of the bank.
2. **Market orders resolve in per-unit lockstep.** Each turn the engine walks both
   players' order lists index by index. At each index both players quote the same
   pre-trade price for one unit, commit, and repeat
   (`kaggle_environments/envs/kaggriculture/kaggriculture.py`, `_process_market`).
   So the *slot order* of our SELLs relative to the rival's decides who sells at
   the higher price. Against a rival whose list is predictable, that is an exactly
   solvable game.

## What v8 is

`main.py` is an Apache-2.0 derivative. Every piece is credited in the file header
and in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).

* **Base: prvsiyan's "The Soil Remembers Rain".** It was the strongest public agent
  I could find: 1.000 score rate in a 6-agent round robin, and it beats every other
  public agent tested.
* **Counter D (shiiin9, via tetsutani's public notebook).** Each turn it searches
  up to 800 orderings of our SELL and fixed-price slots. Each ordering is scored
  with the engine's own per-unit lockstep, against a rival modelled as playing our
  own pre-reorder list. That model is exact against a clone.
* **Sale-race horizon 44** (from the same notebook; the base ships 40/41).
* **Level-2 counter D (new).** Counter D is public, so part of the field now
  reorders its own list the same way. v8 computes that level-1 list too. It then
  chooses the ordering whose margin is best against the *worse* of the two rival
  models (plain clone, or clone running counter D).
* **An entrypoint that cannot raise.** The base's outermost function indexes
  `observation['step']` unguarded.

## Evidence

All runs use `kaggle-environments==1.32.7`, 720 turns and real ladder seeds. The
engine is deterministic per seed, so swapping sides replays the same game. Each
seed is therefore counted once.

### Closed loop: v8 lineage against the public field

On 12 fresh ladder seeds, the level-1 build (base + counter D + horizon 44) against
the base alone, both facing the same field:

| Opponent | Base + counter D + 44 | Base alone |
| --- | --- | --- |
| user's v7 (= public pipe16) | 11/12, +$1,167 | 9/12, +$644 |
| guru master-engine v3 | 11/12, +$1,098 | 9/12, +$574 |
| tetsutani demand (counter D, horizon 40) | 9/12, +$758 | 8/12, +$384 |
| thomastschinkel 2945 | 12/12, +$2,026 | 12/12, +$1,698 |
| ahmed v48 | 12/12, +$4,377 | 12/12, +$4,156 |

Against the user's own submissions: 44/44 against v3 (+$4,502 mean) and 20/20
against v7 (+$1,938).

Level 2 against level 1, on 16 further seeds:

| v8 (level 2) vs | Result | Mean margin |
| --- | --- | --- |
| level-1 build (counter D) | 14 W, 2 T, 0 L | +$30 |
| base alone | 15 W, 1 L | +$380 |

The level-1 build scores +$432 against the base alone, where level 2 scores +$380.
Level 2 gives up a little margin against rivals without counter D. It gets back the
games against rivals that run it.

### Real opponents: the ghost benchmark

`benchmark/ghosts/ladder_ghosts.json.gz` holds the recorded action tape of the
opponent in 367 of this account's own ladder games:

* all of v7's losses and ties
* 60 of v7's wins
* 39-40 losses each from v3, v4, v5 and v6

Replaying a tape against our own recorded side reproduces the original banks to
the dollar. So does replaying it against the live v7 code. Swapping in another
agent answers "what would it have scored against the opponent we actually met, on
the board we actually drew".

The limitation: a ghost cannot react. It is a fair test of production and market
timing against real order flow, but not of adaptive play. The closed-loop tables
above cover that.

| Agent in our seat | All 367 | The 210 v7 games | v7's 110 losses |
| --- | --- | --- | --- |
| what actually happened | 61 W, 39 T | 61 W, 39 T | 0 |
| tetsutani demand | 284 (77%) | 155 | 58 |
| base alone | 304 (83%) | 169 | 77 |
| level-1 build | 323 (88%) | 183 | 86 |
| **v8** | **327 (89%)** | **185** | **87** |

### Tried and rejected

* **Re-routing by shop layout.** The base picks one of 41 tapes from the first two
  unlocked shops. On the 113 ghost games that the table sends to route 105, every
  alternative tested was worse on average, and no shop pair showed a consistent
  gain:

  | Route | Games won (of 113) | Mean margin |
  | --- | --- | --- |
  | 105, the table's choice | 97 | +$2,048 |
  | 107 | 89 | +$1,351 |
  | 100 | 87 | +$1,226 |
  | 103 | 65 | −$5 |
  | 126 | 41 | −$2,648 |

  The table stays as it is.
* **Race horizons 48, 56 and 72.** All were worse than 44 head-to-head against the
  base.
* **Everything in `agents/scratch/`.** The from-scratch agent this repository
  started with finishes about 18% below ladder-level banks. See
  [ARCHITECTURE.md](ARCHITECTURE.md). It is kept for its engine notes and tooling,
  not as a candidate.

## What would move it further

* **Refresh the ghosts after v8 has played a few days.** The losses v8 still takes
  are the next target, and `tools/fetch_ghosts.py` downloads them.
* **Identify opponents.** Running each public agent in the opponent seat against
  our recorded side shows which ladder players run which public code, exactly. For
  those, counter D's rival model can be the real list rather than an assumption.
  This was too slow to finish here: about three games a minute on 4 CPUs.
